# 对核心设计进行三种接口推演与故障演练

2026-10-11。方法：按 codebase-design 的 Design It Twice，用三个独立设计代理分别约束最小接口、最大恢复弹性、普通浏览器调用方。结果是设计分析，**没有运行这些新协议的实现或故障测试**。

产品首版浏览器优先。推演围绕一个问题：怎样把采集、保存、转录、纪要的复杂性集中在深模块中，又不让页面或未来调用方承担不可见失败？

## 方案 A：以持久录音带组织最小入口

接口为 `open(spec)`、`accept(AudioPacket | CaptureSeal)`、`watch(recordId, cursor)`。浏览器拥有 MediaStream 和本地缓冲；后端隐藏去重、持久 ACK、排空、重放与默认纪要调度。人工改稿和行动确认走相邻模块的独立 seam。

它的 depth 来自三个入口背后完整的恢复语义；locality 使可靠性修复集中。删除这个模块后，调用方必须重新承担这些复杂性。代价是生命周期政策固定，复杂输入编排与重新生成操作需要相邻接口；若为方法少不断给 accept 加指令，会退化成伪简单接口。

## 方案 B：用有限命令协议表达恢复与扩展

接口为 `execute(command)`、`read(recordId)`、`watch(recordId, cursor)`。有限命令包括 AttachSource、AppendAudio、SealSource、Finalize、ReviseTranscript、BuildMinutes、ConfirmAction、Delete。回执包含版本、cursor、连续输入水位和缺口；不同命令有独立幂等与权限语义。

它的 depth 在于隐藏多来源、跨刷新恢复、并发修订与删除竞态；接口学习负担高于方案 A，适合后端协议、导入和未来客户端。通知日志只服务可靠交付，权威状态仍在关系模型中；无需全量事件溯源。代价是协议版本与幂等存储较重，必须限制命令集合，避免万能业务总线。

## 方案 C：让页面绑定记录体验 facade

页面只订阅 view model，绑定当前可用 controls，并调用 saveNote、saveMinutes、confirmAction、openEvidence。状态包含本地已保存、云端已保存、待上传、缺口、纪要新鲜度；provider、sequence 和重试不进入页面逻辑。

授权按钮的 `activateFromGesture()` 必须同步触发浏览器权限请求，异步结果再更新状态。页面不能先 await 建会网络请求再请求 getDisplayMedia。该 seam 围绕普通人的默认流程，locality 很好；代价是带产品交互政策，不适合直接当自动化协议，测试时也要验证语义状态而非固定中文文案。

## 推荐组合与取舍

| 比较点 | A 最小入口 | B 有限命令 | C 体验 facade |
| --- | --- | --- | --- |
| 普通页面学习成本 | 中 | 高 | 低 |
| 输入补传与并发表达 | 可支持，需隐含政策 | 最清楚 | 隐藏在内部 |
| 人工编辑与行动所有权 | 相邻模块 | 有限命令但易膨胀 | 产品操作清楚 |
| 未来导入/客户端 | 中 | 高 | Web 专用 |
| 最大风险 | 表面少方法、隐含规则多 | 万能命令总线 | 把显示状态当后端权威 |

**推荐 C 作为 Web 外部 interface，B 的有限恢复协议作为内部后端 seam，并保留 A 的音频交付简洁性。**不要实现三套核心；单一 Record Commit implementation 管内容提交，facade 与 HTTP/SSE adapter 共同复用。纪要编辑、行动确认保留明确所有权，避免扩成一个无所不管的会议模块。

一处 seam 有真实生产 adapter 和可控测试 adapter 才值得抽象。纯计算直接放入 module；数据库原子性用真实测试实例验证，不能只靠内存替身。

## 以不同角色挑战设计

| 视角 | 提出的挑战 | 收敛规则 | 后续证据 |
| --- | --- | --- | --- |
| 普通使用者 | 我授权共享后为什么没录到对方？ | 检查实际音轨和电平，解释来源，禁止静默降级 | 实机来源矩阵 |
| 实时工程 | 800ms 的目标会不会导致尾音丢失？ | partial 快显；durable final 独立提交；停止有屏障 | 时序 trace 与尾音样本 |
| 数据一致性 | 页面显示 final，API 却失败怎么办？ | final 提交和 outbox 同事务；UI 区分暂定/已保存 | 提交前后崩溃测试 |
| AI 质量 | 错误转录被模型说得更肯定怎么办？ | 引用确定版本，未知保留，候选由人确认 | 断言支持率及失败集 |
| 隐私与信任 | 关闭留存为何还上传声音？ | 分开云处理、临时缓冲与长期留存 | 数据流与 TTL 验证 |
| 成本与运营 | 双源、翻译和重试会不会失控？ | 分能力预算、额度、重试上限、成本观测 | 每分钟成本与压测 |
| 架构维护 | 为什么不立即换 Go/微服务？ | 先解决契约；仅以 profiling 和运维数据推动替换 | 契约等价与性能对比 |
| 产品策略 | 借鉴 DeepPage 会不会做成大而全？ | 先完成一次可信会议记录，再评估知识和自动化 | 用户复用率与留存 |

以上是角色视角模拟，不是外部专家评审或真实用户访谈。

## 逐步演练最容易漏掉的失败

**断网后停止。**服务端只有 1–40，浏览器缓存 41–60。用户停止，seal 声明最后 60；Finalize 等待缺口，仍允许 41–60 补传。刷新后重复块返回原 ACK；如果缓存丢失，只能形成有缺口记录，不能宣称完整。

**持久化后 ACK 丢失。**第 100 块对象与元数据已提交，响应前服务崩溃。重传身份/hash 相同，取回原回执；outbox 继续投递，不能重复触发纪要或增加输入量。

**停止后 final 迟到。**采集已停，ASR 尚有尾部结果；转录保持 draining。adapter 排空并提交后才建立封存版本。超时记录明确范围和原因，不能仅靠 socket.close 宣告完成。

**人已纠错，旧纪要才返回。**worker 输入为 revision 7，当前已到 8。旧结果保存为过期草稿，不能覆盖新纪要或人工编辑；新生成使用 revision 8。只检查任务成功状态不足以保证新鲜度。

**分享时权限发生变化。**已打开 viewer 后撤销令牌，历史补取、实时订阅与缓存均受撤销约束。只禁止新打开页面会泄露后续内容。

**删除与补传/任务完成竞态。**删除提交 tombstone/generation；随后到达的旧输入、ASR 与 LLM 结果必须拒绝。物理清理单独报告进度，第三方留存不能由本地状态代言。

**音频来源中断但网络正常。**标签页关闭导致音轨 ended，UI 从正常记录切换到中断提示并记录缺口；要求用户点击重新授权。不能用持续收到空白块证明会议仍在录。

## 仍需实证的关键问题

1. 目标人群的实际会议应用和浏览器/系统组合，能否通过 Web 共享得到必要声音？
2. 中文混语、口音、重叠说话与术语的真实识别和纪要质量，能否达到可用门槛？
3. 用户是否愿意保留临时音频以换取恢复能力，对云处理和分享的理解是否一致？
4. 当前 Node 传输、采样与 worker 的资源消耗何时成为瓶颈，是否有换传输或运行时的必要？

这些问题决定先导实验与支持范围；不能通过架构图或 CodeGraph 节点数推定答案。
