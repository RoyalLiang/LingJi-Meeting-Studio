# 保存、检索与长会议的性能边界

## SQLite 按集合保存高频内容

记录主体保存在 `aggregates`，启用压缩时主体载荷保存在 `aggregate_payloads`。`chunks`、`segments`、`events` 分别保存在 `record_collections`，与主体、列表投影和事件投影处于同一事务；小状态更新不再重写未变化的集合行。读取在同一 SQLite 快照内取得主体与集合，校验集合计数和顺序。跨进程写入由版本标识使缓存失效。

这减少写入放大，仍会比较集合内容，并非严格 O(1) 写入。纪要历史和任务状态仍属于主体。SQLite 继续使用 WAL 与 `synchronous=FULL`，音频持久化确认不提前。Postgres/S3 使用原有适配器，未套用 SQLite 集合格式。

旧的普通 JSON 和压缩主体继续可读，在后续写入时迁移。首次引入集合表前，已有记录的数据库会一致性备份到数据根目录的 `records.pre-collections-v1.sqlite`，已有备份不覆盖。备份创建失败会阻止迁移。

旧版本不能直接读取新集合格式。回退需要先停止全部后端、保留整个当前数据目录，并从一致性备份恢复；迁移后的新增内容需另行导出。不要将旧备份与当前 WAL／SHM 文件混用。

开发工具需要只读数据库时，应在读事务内使用 `hydrateRecordCollections`；不能只解析主体后将缺失集合当作空数组。学习快照导出已使用相同读取规则。

## 列表与检索使用投影

目录概览、创建配额和删除状态读取轻量投影。SQLite 搜索使用 FTS5 trigram 缩小三字符及以上查询的候选范围，并保留字面子串核对；较短查询沿用子串匹配。用户、工作目录、删除与保留期过滤继续生效。跨会议分析的显式生成仍可能读取完整来源，不能将当前实现描述为百场会议知识库。

## 音频队列保持持久化边界

浏览器 IndexedDB 新片段保存二进制 PCM，兼容已有 Base64 队列。二进制 API 直接传输字节；旧 API 和人工下载的故障备份仍使用 Base64。音频身份、摘要、重传去重与按来源上传规则不变。

桌面本机优先取得 API 的持久化回执，再保存停止游标并确认 Rust 队列；失败或 2 秒超时后退回 IndexedDB。远程 API 模式继续本机排队。当前仍存在 Rust／WebView／代理跨层传输，尚未实现 Rust 直接入库。

SSE 在同一进程收到仓库变更时推送，保留每秒跨进程检查和鉴权。后台 worker 仍有定时调度；尚未实现 PG LISTEN/NOTIFY。WAV 响应按顺序输出，最多预读四个片段。

## 大段文字与音频导入

逐字记录和译文每页最多挂载 60 段，分页不丢弃全文搜索范围。编辑锚定片段，暂停阅读后不随新内容翻页。已有编辑草稿在收起记录后保留。

单个音频文件继续限制为 64 MB。16 kHz、16 位 PCM WAV（单／双声道）按片段读取并混为单声道，超过 15 分钟仍可导入。其他需要浏览器完整解码的格式先检查时长，超过 15 分钟时提示拆分；解码直接使用 16 kHz，避免额外整场重采样缓冲。导入采用 10 秒分片和有界批次。

当前不支持任意长压缩音频的流式解码。多声道、特殊编码及真实设备的内存峰值仍需独立验收。

## 验证范围

自动化检查覆盖事务回滚、跨连接读取、迁移备份、旧队列恢复、停止游标、字面搜索、长列表编辑和音频顺序。合成基准与真实模型的合成输入只能验证对应路径；不替代连续双路录音、原真实会议、PG/S3 或安装后的现场验收。
